# Threat model

What Sealed Recipes protects, from whom, and where the protection ends.

## Assets

1. **The recipe**: wiring, secret params, prompts. This is the creator's edge.
2. **Buyer inputs**: wallet, thresholds, the fresh recipient address.
3. **Money**: run payments in escrow, payouts, each recipe's guarantee deposit (available and locked cover), and the integrity of each recipe's market price.
4. **Buyer funds** touched by a workflow, such as dust swept by CLNP.

## Adversaries and mitigations

| Adversary | Attack | Mitigation | Residual risk |
|---|---|---|---|
| Marketplace operator | Read or copy recipes | Recipes are sealed in the creator's browser to the runner's attested key. The server only stores the envelope; `tests/runner.test.ts` checks that `server/` never imports the decryption function | Metadata: which parts a recipe bills is public, because it has to be for attribution. In local mode the browser compares the attestation with runner keys served by the marketplace's contract mirror, so a malicious marketplace could substitute keys; in production that view must come from NEAR RPC |
| Marketplace operator | Read buyer data or link the buyer to the fresh address | Inputs are sealed to the runner. Part logs, wallet requests and the result are sealed by the runner to a one-time key generated in the buyer's browser. Event streams and approvals require a per-run token returned only to the buyer | The marketplace sees coarse progress (which part started or finished) and the payment quote. Recipe-intent quotes are sealed to the buyer too. If the buyer picks a guaranteed quote, `expected`, `promised`, `cover` and later `delivered` are written on-chain (that is what makes the promise enforceable); "No guarantee" keeps them off-chain |
| Anyone | Run an expensive recipe after paying for a cheap one | The runner takes the recipe id from the paid run on-chain and checks the sealed recipe against the hash snapshotted in that run | — |
| Buyer / competitor | Reverse-engineer a recipe from its outputs | Outputs only reveal results. Params and prompts stay inside the runner | Black-box probing over many paid runs, which costs money every time |
| Chain observer | Link the buyer to the fresh address | Swaps use `confidentiality: "basic"` in 1Click, so deposits and withdrawals cannot be linked on-chain. The fresh key is made in the browser; only the address is sealed | Timing and amount correlation by a determined observer. `advanced` confidentiality is available and is a one-param change in the part |
| Malicious runner operator | Read plaintext | Production runner runs in an Intel TDX CVM. Keys come from dstack `getKey` and never leave the enclave. Clients verify REPORTDATA = sha256(codehash, keys, nonce) | TEE side channels. Local-dev mode has **no** hardware protection, and the UI says so |
| Malicious or buggy runner | Bill parts that didn't run / bill extra parts | `parts_used` must be a sub-multiset of the recipe's on-chain part list. Reports must be signed by the registered key | A compromised runner could report success for a run that failed. Mitigation: pin `codehash` to the audited release and verify hardware attestation; quote signatures are already verified on-chain (`srs-quote-v3`) |
| Replay | Re-settle a run | `report_run` requires `Pending`; the signature covers contract id, run id and output hash | — |
| Forged attestation | Make clients seal to an attacker key | Fresh nonce, key binding in report_data, possession signature, keys must match `add_runner`, and Intel DCAP chain via `scripts/verify-quote.ts` | Owner key compromise (use a DAO as owner) |
| Part author | Exfiltrate buyer data | Parts only reach hosts declared in `capabilities` (`guardedFetch`). Admission by tier (SRS-1 §11): a part that reaches any host outside the known NEAR data hosts, or calls a model, needs an appointed reviewer, who confirms every host is needed. Every part's code is in the runner's code hash | A part can still send data to a host it declared and a reviewer accepted. Buyers see each part's capabilities before paying |
| Part author | Ship malicious code (backdoor, drain, hidden host, time bomb) | Admission by tier. Every submission: conformance, static and security checks (imports, `process`, globals, code generation, prototype tricks, hidden strings, undeclared hosts) and a behaviour test in the sandbox as a quote and as a run. Open parts run only in the sandbox; parts that send data somewhere new need one appointed reviewer; parts that ask buyers to sign need two independent ones. The runner refuses any part whose code or manifest differs from its signed release record | Static checks and sample-input tests can be evaded by code that behaves only on certain accounts, dates or amounts; that is what the human checklist ("no special-cased accounts or amounts") is for, and why signing parts need two reviewers. Review is not proof |
| Open-tier part | Escape the sandbox | Own process; Node permission model (read-only access to its own file; no writes, child processes, workers, native addons); code generation from strings disabled; network functions and `process` escapes removed before load; only IPC out; killed at `max_ms`; no secrets passed in | The Node permission model is not a security boundary against a Node or V8 exploit, and does not restrict raw sockets on its own (the removed network functions and the import filter do). Production target: WASM with fuel metering inside the TEE |
| Appointed reviewer | Approve a malicious part, or block a competitor | Signing parts need two different reviewers; reviewers never review their own parts; every approval is signed and public in the release log, with the checklist the reviewer confirmed; the open tier needs no reviewer at all | Colluding reviewers can admit a malicious signing part, and reviewers can stall a submission. Planned: reviewer stakes slashed for approving a part later shown malicious; several runners pinning their own releases |
| Owner | Appoint compliant reviewers, or skip review in a release | The reviewer set and the release log are inside the runner's code hash, so every change is visible to anyone who verifies the attestation; the runner checks reviewer signatures against the set | The owner controls the set and cuts releases: one key is the trust model today. Use a multisig or DAO as owner |
| Solver / 1Click | Underpay a run | `ft_on_transfer` requires `amount ≥ price_per_run`. Below that it panics and the token refunds the sender, or, when `on_behalf_of` is set (Intents delivery), the full amount is credited to the buyer with `transfer_rejected` | — |
| Buyer | Pay, then claim a refund | Only the runner's signed `fail`/`abort` report or a 15-minute timeout refunds | — |
| Buyer | Drain the bond: get a bonded quote with a full wallet, empty the wallet, then pay with the quote | Right before executing, the runner re-prices the run in the TEE; if the fresh promise is below 98% of the quoted one it signs `abort`: price refunded, cover returned to the bond, `aborted` counter (not `failed`) goes up. `npm run attack:drain` runs this attack against the demo | Draining *during* execution (after the re-check, or depositing less than asked) was the remaining path: the TLA+ model found it (`verification/tla/results/MC_v3.log`: pay, re-check, deposit nothing complete, collect the whole cover). Fixed: bonded runs report `delivered` credited with whatever the buyer withheld after the re-check, and TLC checks `NoBondDrain` over 22.7M states. Market moves in the seconds between re-check and execution are not insured |
| Buyer / relayer | Reuse or redirect a quote (pay it twice, pay it for another job or account, replay it after the recipe changes) | The signed message binds contract, recipe, recipe version (`sealed_hash`), `job_hash`, sealed inputs (`inputs_hash`) and buyer; each quote can be used once; every runner-side failure after a verified payment signs a `fail` report, so a paid run never waits for the timeout | — |
| Creator | Swap the workflow under buyers who rely on its track record, or mid-run | A new version is announced on-chain (`recipe_update_scheduled`) and takes effect only after the notice period (`update_delay_ns`). Each paid run keeps the version it paid for, the vault keeps every version, and quotes are bound to a version. Model-checked in `VersionedRecipes.tla` | Repeat buyers and agents still have to watch the announcements. The parts list cannot change; a different parts list is a new recipe |
| Runner crash or restart mid-run | Lose a long workflow, re-run an irreversible step, or ask the buyer to sign twice | Signed, sealed checkpoints stored before every irreversible step; resume from the last one; swap intents and relayed approvals replayed (`DurableRuns.tla`: `DepositsOnce`, `PaidExactlyOnce`, `EventuallyDone`); `npm run test:durable` | Steps without side effects that finished after the last checkpoint run again; they are pure reads |
| Marketplace | Withhold the latest checkpoint to force a replay | Checkpoints are signed by the runner, and in checkpoint mode every part's state hash is also on-chain, so a stale checkpoint is visible. The runner does not move past an irreversible step until the checkpoint is stored | In `"final"` mode only heartbeats go on-chain, so detection there relies on the runner's own records |
| Partial swap failure | Some swaps execute, others fail, leaving the buyer half-converted | `intents.atomic-swap` signs one NEAR Intents bundle: the Verifier executes every token_diff and the withdrawal together or not at all; on failure the deposits stay in the buyer's own intents.near balance | Atomic bundles are public on NEAR (no confidentiality mode); the confidential 1Click swaps are not atomic. Recipes choose one or the other, and the privacy label says which |
| Lost creator source | A creator cannot edit a published recipe because only the runner can read it | Each version is also sealed to a key derived from the creator's wallet signature (NEP-413 signMessage); re-derivable on any device | A wallet with several access keys yields one creator key per key; the local demo derives a demo key from the account name |
| Long-running run | Buyer reclaims mid-way and keeps finished work for free | `reclaim_run` counts from the last on-chain checkpoint, not from payment; in checkpoint mode parts already done are paid and not refunded | — |
| Paying buyer / competitor | Infer the recipe from many runs (black-box probing) | Every probe is a paid run; outputs reveal results, not params | Simple recipes can be inferred. Planned: per-buyer rate limits, minimal outputs, flagging unusual input patterns |
| Creator | Inflate their own price by buying their own runs (wash demand) | Each fake run pays the protocol, runner and part fees for real, the price rises at most 12.5% a period, and the ceiling is fixed by the creator in advance; buyers compare signed prices across recipes and can set `max_price` | A creator willing to pay the fees can hold the price near the ceiling. Counting only quoted runs from distinct, funded buyers would raise the cost |
| Marketplace / keeper | Delay applying ended pricing periods to keep an old price | Every payment applies ended periods itself before checking the price, and anyone can call `update_price`; views compute the rolled price | — |
| Runner | Quote a price outside the creator's band | The contract rejects any quoted price outside `price_floor..price_ceiling`; the price is inside the signed message, so it can't be changed in transit | A compromised runner could quote anywhere inside the band |
| Creator | Withdraw the guarantee deposit right after quoting | Each quote's cover is locked when the run is paid; `withdraw_bond` can only take the unlocked part (`bond_available`), and only the creator can call it | A quote not yet paid is not backed: cover is checked against `bond_available` at payment, and a payment whose cover is no longer available is rejected and refunded |
| Competitor | Rebuild the recipe independently from the public part list | None technical: the part list must be public for attribution | Secrecy, unlike a patent, does not stop reinvention. The market prices the shrinking edge |
| Runner key compromise or loss | Decrypt every recipe, or lose them | Keys derived in the TEE (dstack KMS), never exported | One runner key seals all recipes today. Planned: per-recipe keys, rotation and re-sealing across several runners |
| Runner image auditor | Read part authors' code | Parts are reviewed or automatically admitted code in a pinned image (SRS-1 §11) | Not in this build, but possible on NEAR: parts can be sealed to the runner like recipes, run as OutLayer closed-source WASM in TDX, or run as their own attested TEE service |
| Recipe creator | Win buyers with inflated quotes | Quotes are produced by the attested runner from a dry run, not typed by the creator, and signed by the runner key; the promise is the post-slippage minimum | Market moves between quote and run. Shortfalls are paid from the bond up to the signed `cover`, which the buyer sees in the quote |
| Under-bonded recipe | Promise more than it can cover | The runner signs `cover = min(promised, bond_available)` into the quote; the contract rejects the payment (`bond below quoted cover`) if the bond can no longer lock that much, so the cover the buyer saw is the cover they get | A promise larger than the bond is only covered up to `cover`; the quote shows both |
| Recipe creator | Make a closed-model recipe look open or confidential | Risk, privacy and disclosure labels are computed by the marketplace from the on-chain `parts`, never taken from the creator's listing; the runner refuses a sealed recipe whose parts differ from the on-chain list; AI parts call the model their manifest discloses, not a recipe param | — |
| Runner | Report a false `delivered` value | `delivered` is signed by the attested runner key and covered by the code hash | Same trust as run reports: needs hardware attestation (and later on-chain DCAP) to be meaningful |
| Quote spammer | Burn runner compute with dry runs | 12 quote requests per minute per client; dry runs obey each part's resource limits | A quote fee would price this properly on-chain |
| Part supplier | Withdraw or reprice a model or service a recipe depends on | Bundled parts are pinned code the author can't switch off; SRS-1 labels withdrawal risk (closed models high, remote services medium); drop-in swap search finds replacements | Remote and closed-model parts can still disappear. Planned: fallback parts, notice periods, supplier bonds |
| Runaway part | Loop or call models until the bill explodes | Per-part limits on time, HTTP calls, model calls and output size; when one trips, an AbortController cancels the part's in-flight and later requests; the buyer's price is fixed up front and the run is refunded | For open-tier parts the sandbox kills the process at `max_ms`, so a CPU-bound loop is stopped. For reviewed and signing parts, which run in-process, limits are cooperative and a CPU-bound loop is not preempted; review is what stands in for that, and WASM with fuel metering is the production target |
| AI model provider | Read sealed prompts | AI parts call NEAR AI Cloud **private** models. TLS terminates in the gateway TEE, and every response is signed by the attested TEE key and checked | Gateway-kind signatures are checked against the gateway's key. Gateway attestation is not re-verified inside the part |
| Key revocation recipe (KEYS) | Lock the owner out, or revoke keys it should not | The part only ever deletes function-call (app) keys; full-access keys are reported for review, never removed. The DeleteKey transaction is shown in the wallet dialog and signed by the owner. The result is confirmed by re-reading the key list | The rules decide which app keys are risky; a wrong blocklist entry revokes a key the user wanted (they sign in to that app again) |
| Contract check recipe (CHEK) | Give a false "low risk" on a phishing contract | Facts come from RPC (code, full-access keys, NEP-330 metadata), and the AI verdict is signature-checked against the attested model. A rules-only part can be swapped in | A low verdict is not a guarantee: a locked contract with published source can still be malicious by design. The report says so |

## Custody

The runner **never holds user funds**. Parts that move funds (`wallet:approve`) only prepare transactions, the buyer's wallet signs them, and the approval dialog shows the raw `signAndSendTransactions` payload.

## Known gaps (v1)

- No storage deposits on `register_part`, `publish_recipe` or orders. This is a spam vector on mainnet.
- Part admission relies on owner-appointed reviewers for parts that send data somewhere new or ask buyers to sign (SRS-1 §11). The open tier is permissionless; the rest is permissioned and auditable, not decentralized yet.
- The contract owner approves runners after verifying attestation off-chain. On-chain DCAP verification (as Shade Agent contracts do) is the next step.
- 1Click (the service) sees swap requests, including the fresh recipient. Confidential intents protect against chain observers, not against the 1Click operator.
- The local demo has no hardware TEE, mock services and a demo wallet. See "What is real" in the README.
- IP protection is by secrecy, not exclusivity: it stops copying, not probing at scale or independent reinvention. See "What the sealing protects" in the README.

## Regulatory exposure

Revenue shares, dividends and share trading were removed (git tag `archive/revenue-shares`) so that nothing in the product is plausibly an investment contract. Participants are paid for services (runs, parts, execution), buyers are paid compensation for a shortfall, and the guarantee deposit is collateral the creator posts and controls: it earns no return and nobody can buy into it. This is a design measure, not legal advice; an operator still has to consider payments, consumer and tax rules where it operates.
